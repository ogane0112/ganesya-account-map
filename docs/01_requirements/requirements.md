# アカウント管理アプリ 要件定義書

- 版数: v0.4(ドラフト・ライブラリ管理方針を反映)
- 作成日: 2026-08-09
- 作成者: (本人)
- 対象: 個人利用のアカウント管理アプリ

---

## 1. 背景・課題

近年、ゲームやサービスごとにアカウントが乱立し、以下のような管理上の課題が発生している。

- Steam、バンダイナムコID、各種ゲームプラットフォームなど、サービスごとにアカウントが存在する
- ログイン方式がサービスによって異なり、把握が難しい
  - ID/パスワードによる直接ログイン
  - Google OAuth によるログイン
  - LINEログインによるログイン
  - バンダイナムコカードのような「物理カード/コード連携型」の紐づけ
- 「どのアカウントが、どのログイン方式で、どのサービスに紐づいているか」が可視化されておらず、管理が煩雑になっている
- 紐づけの構造(親アカウント・子アカウントの関係)が複雑で、忘れると復旧が困難

## 2. 目的

すべてのアカウント・ログイン方式・紐づけ関係を一元管理し、以下を実現するアプリを構築する。

1. どのサービスにどのアカウントでログインしているかを即座に確認できる
2. OAuthやカード型連携など、紐づけの構造を可視化できる
3. **パスワードそのものは保存せず**、「どの認証情報管理ツールに保存されているか」を記録・参照できる
4. 更新期限や見直しが必要なアカウントを把握できる

> **設計方針(重要):** 本アプリはパスワードマネージャーの代替ではない。パスワード自体の保管はGoogleパスワードマネージャー、1Password、Apple パスワード、Microsoft Edge等の**既存の専用ツールに委ねる**。本アプリはその「参照先(どこに保存したか)」と「アカウント間の紐づけ構造」の管理に特化する。これにより機微情報の漏えいリスクを大幅に低減する。

## 3. スコープ

### 対象に含む

- 個人が保有する各種オンラインサービスアカウントの登録・管理
- ログイン方式(ID/PW、OAuth、カード型連携、SSOなど)の記録
- アカウント同士の紐づけ関係(親子関係)の管理
- 検索・フィルタ・分類
- 機微情報(パスワード等)の暗号化保管

### 対象外(初期リリースでは扱わない)

- 複数ユーザーでの共有・チーム管理機能
- 自動ログイン・自動入力(ブラウザ拡張的な機能)
- クレジットカード等の決済情報そのものの管理(サービスとの紐づけ「有無」の記録のみ行う)

## 4. 想定ユーザー

- 本人(個人開発・個人利用)
- ゲームアカウントを中心に、多数のオンラインサービスアカウントを保有し、管理に課題を感じている人

## 5. 機能要件

### 5.1 アカウント登録・管理(基本機能)

| 項目 | 内容 |
|---|---|
| 新規登録 | サービス名、アカウント識別子(ID/メールアドレス等)、カテゴリ、ログイン方式、メモを入力して登録 |
| 一覧表示 | 登録済みアカウントを一覧表示(カード形式/テーブル形式を切替可能) |
| 詳細表示 | 個別アカウントの詳細(紐づけ関係含む)を表示 |
| 編集・削除 | 登録内容の編集、不要になったアカウントの削除(アーカイブ機能も検討) |
| 検索 | サービス名、カテゴリ、ログイン方式などで検索 |
| フィルタ・ソート | カテゴリ別、ログイン方式別、最終ログイン日別などで絞り込み・並び替え |

### 5.2 ログイン方式の管理(本アプリの核心機能)

サービスごとに異なるログイン方式を「タイプ」として明確に区別して登録できるようにする。

| ログイン方式タイプ | 説明 | 記録する情報の例 |
|---|---|---|
| ID/パスワード直接ログイン | サービス独自のアカウントで直接ログイン | ID、**パスワードの保存先(下記参照)** |
| OAuth連携ログイン | Google、Apple等の外部認証を利用 | 連携先プロバイダ(Google/Apple等)、連携に使ったアカウント |
| SNSログイン | LINEログイン、X(Twitter)ログイン等 | 連携先SNS、連携に使ったアカウント |
| カード/コード型連携 | バンダイナムコカードのような物理カードやコードでの紐づけ | カード番号(下4桁等マスク推奨)、紐づけ先アカウント、発行日 |
| ゲスト/端末紐づけ | 特定の端末やゲスト状態でのみ有効なアカウント | 端末名、備考 |

**ポイント:** 1つのサービスアカウントが「複数の連携」を持つケースに対応する。
例: `バンダイナムコID` は「ID/PW」でも「Googleアカウント」でもログイン可能、かつ「バンダイナムコカード」で他のゲーム内アカウントと紐づいている、といった多重構造を記録できるようにする。

### 5.3-a パスワード保存先の記録(パスワード自体は保存しない)

ID/パスワード方式の場合、パスワードの値そのものは**アプリ内に一切保存しない**。代わりに「どの認証情報管理ツールに保存されているか」を選択式で記録する。

| 保存先(認証情報管理ツール) | 備考 |
|---|---|
| Google パスワードマネージャー | Chromeやアカウント設定と同期 |
| Microsoft Edge(パスワード) | Edge内蔵の保存機能 |
| Apple パスワード(iCloudキーチェーン) | iOS/macOSの保存機能 |
| 1Password | 専用パスワードマネージャー |
| Bitwarden | 専用パスワードマネージャー(他ツールの例) |
| ブラウザ以外の手帳・メモ等 | アナログ管理の場合 |
| その他(自由記述) | 上記に当てはまらない場合 |
| 不明・要確認 | 保存先を忘れてしまった場合のフラグ |

これにより、「このアカウントのパスワードを変更したい/確認したいときは、どのツールを開けばよいか」が一目でわかるようになる。

### 5.3 紐づけ関係(親子関係)の可視化

- あるアカウントが「どのアカウントの認証情報を使ってログインしているか」を親子関係として登録できる
  - 例: `Steamアカウント` ←(Googleログイン)← `Googleアカウント`
  - 例: `ゲームA内アカウント` ←(カード連携)← `バンダイナムコID` ←(OAuth)← `Googleアカウント`
- 紐づけ関係をツリー図・相関図として可視化する画面を用意する
- 「このGoogleアカウントを失うと、どのサービスに影響するか」を逆引き表示できる

### 5.4 機微情報の取り扱い方針

- **パスワード自体、秘密の質問の答え、2FAのバックアップコード等の機微情報は本アプリ内に一切保存しない**
- 保存するのは「保存先ツールの名称」という**参照情報(メタデータ)のみ**
- カード番号など一部識別情報を記録する場合も、下4桁等のマスク表示を基本とし、フルの番号は保存しない
- この方針により、本アプリ自体が漏えい・攻撃対象になった場合でも実害(パスワード漏えい)を防げる
- 「パスワード強度チェック」「使い回し検知」等の機能は、各パスワードマネージャー側の機能に委ね、本アプリのスコープ外とする

### 5.5 期限・状態管理

| 項目 | 内容 |
|---|---|
| 最終ログイン日 | 手動記録または連携時に自動記録 |
| 更新期限 | サブスクリプションやカードの有効期限などがあれば登録し、期限が近づいたら通知 |
| ステータス | 「利用中」「休眠」「解約済み」「要確認」などのラベルを付与 |
| 2段階認証の有無 | 2FA設定済みかどうかのフラグ管理 |

### 5.6 通知・アラート

- 長期間ログインしていないアカウントの一覧表示(休眠アカウント検出)
- パスワード使い回し・弱いパスワードの警告
- 更新期限が近いアカウントのリマインド

### 5.7 データ入出力

- CSV/JSON形式でのエクスポート(バックアップ用途)
- インポート機能(他パスワード管理ツールからの移行を想定)
- 暗号化バックアップファイルの作成

### 5.8 カテゴリ・タグ管理

- カテゴリ例: ゲーム、SNS、金融、通販、サブスク、仕事、その他
- 自由記述のタグ付けにも対応(例: 「PS5」「Steam」「休止中」等)

## 6. 非機能要件

| 分類 | 要件 |
|---|---|
| セキュリティ | パスワード等の機微情報は本アプリ内に保存しないことを大原則とする(5.4参照)。アプリが記録する情報(サービス名、連携構造、保存先ツール名等)自体も機微性があるため、マスターパスワードまたは生体認証でアプリ全体をロックする |
| サプライチェーンセキュリティ | 依存ライブラリは必要最小限とし、導入前に脆弱性(CVE)情報を確認する。詳細は9.5参照 |
| データ保管場所 | 初期版はローカル保存(端末内DB)を基本とし、クラウド同期はオプションとして検討 |
| 可用性 | オフラインでも閲覧・編集ができること |
| バックアップ | 定期的なローカルバックアップ、および手動エクスポート機能 |
| 拡張性 | 将来的な複数端末同期、モバイルアプリ化を見据えた設計とする |
| ユーザビリティ | 紐づけ構造が直感的に理解できるUI(図示)を重視する |
| パフォーマンス | 数百件規模のアカウント登録でも一覧表示・検索が快適に動作すること |

## 7. データモデル(概要)

### Account(アカウント)

| フィールド | 型 | 説明 |
|---|---|---|
| id | UUID | 一意識別子 |
| service_name | 文字列 | サービス名(例: Steam、バンダイナムコID) |
| identifier | 文字列 | ID・メールアドレス等 |
| category | 文字列 | カテゴリ(ゲーム/SNS/金融等) |
| status | 文字列 | 利用中/休眠/解約済み等 |
| created_at | 日時 | 登録日 |
| last_login_at | 日時 | 最終ログイン日(任意) |
| expiry_date | 日時 | 更新期限等(任意) |
| notes | 文字列 | メモ |

### LoginMethod(ログイン方式)

| フィールド | 型 | 説明 |
|---|---|---|
| id | UUID | 一意識別子 |
| account_id | UUID | 紐づくAccountのID |
| type | 列挙型 | ID_PW / OAuth / SNS / Card / Device |
| provider | 文字列 | Google、LINE、バンダイナムコカード等 |
| linked_account_id | UUID(任意) | 連携先が本アプリ内の別Accountの場合、そのID |
| credential_manager | 列挙型(任意) | パスワードの保存先(Googleパスワードマネージャー/Edge/Apple パスワード/1Password/Bitwarden/その他/不明) ※ID_PW方式の場合のみ使用。**パスワードの値自体は保存しない** |
| has_2fa | 真偽値 | 2段階認証の有無 |

### Relation(紐づけ関係・親子構造)

| フィールド | 型 | 説明 |
|---|---|---|
| id | UUID | 一意識別子 |
| parent_account_id | UUID | 親(認証元)アカウント |
| child_account_id | UUID | 子(連携先)アカウント |
| relation_type | 文字列 | OAuth連携/カード連携/端末紐づけ等 |
| note | 文字列 | 補足情報 |

## 9. 技術要件・実装方針

個人利用・セキュリティ重視・自前サーバー運用の手間を避ける、という方針から、**Cloudflareのサーバーレス構成**を採用する。

### 9.1 全体構成

```
[自分の端末]
    ↓ Googleアカウント等でログイン認証(Cloudflare Access)
[カスタムドメイン: accounts.yourdomain.com] ← Cloudflare Accessで保護
    ↓
[Cloudflare Pages(フロントエンド) + Pages Functions(バックエンドAPI)]
    ↓
[Cloudflare D1] ← Account / LoginMethod / Relation テーブル
```

### 9.2 構成要素

| 要素 | 採用サービス | 役割 |
|---|---|---|
| ホスティング(フロントエンド) | Cloudflare Pages | SPA/静的サイトの配信 |
| バックエンドAPI | Cloudflare Pages Functions | アカウントCRUD、検索、紐づけ関係の取得等のサーバーレス処理 |
| データベース | Cloudflare D1(SQLite互換) | 7章のデータモデル(Account/LoginMethod/Relation)をそのままテーブル化 |
| アクセス制御 | Cloudflare Access(Zero Trust) | 許可するメールアドレス(自分のGoogleアカウント等)のみログイン許可 |
| ドメイン管理 | Cloudflareで管理するドメイン/サブドメイン | カスタムドメイン(例: accounts.yourdomain.com)を用意 |

**採用理由:** 自前でVPNサーバーやアプリサーバーを構築・保守する必要がなく、Cloudflareのプラットフォーム内で「ホスティング」「API実行」「DB」「アクセス制御」がすべて完結する。ポートの開放や自前サーバーのOS・セキュリティパッチ管理が不要になり、個人開発として運用負荷を大幅に下げられる。

### 9.3 アクセス制御の設定方針

Cloudflare Pagesは公開直後は誰でもアクセス可能なため、以下の2段構えでAccess保護を設定する。

1. **カスタムドメイン側の保護**: Zero Trustダッシュボードで `accounts.yourdomain.com` 用のAccessアプリケーションを作成し、許可メールアドレスを自分のアカウントのみに限定する
2. **デフォルトの `*.pages.dev` ドメインの保護**: `*.pages.dev` は裏口として使われる可能性があるため、Pagesプロジェクトの設定で "Enable access policy" を有効化し、別途 `*.pages.dev` 用のAccessアプリケーションも作成して塞ぐ

上記どちらか一方だけでは不十分(片方が抜け道になる)なため、必ず両方設定する。

### 9.4 将来拡張

- モバイルアプリ化する場合も、Cloudflare Access はブラウザベースの認証のため、APIエンドポイントに対しては別途トークン認証(Service Tokens等)の検討が必要になる
- D1の容量・パフォーマンス上限に達した場合は、他のDB(Cloudflare製 or 外部)への移行も選択肢として残す

### 9.5 ライブラリ・依存関係の管理方針(セキュリティ要件)

本アプリは機微性の高い情報(アカウント一覧・紐づけ構造)を扱うため、サプライチェーンリスクを抑える目的で、依存ライブラリの導入・管理について以下を必須ルールとする。

| 方針 | 内容 |
|---|---|
| **最小限の原則** | 外部ライブラリは必要最小限に留める。標準機能や自前実装で代替できる場合は、ライブラリを追加しない |
| **パッケージマネージャー** | **pnpm** を使用する(npmは使用しない)。理由: `node_modules` の依存関係がより厳密に解決され、意図しない依存(幽霊依存)の混入を防げるため |
| **導入前の脆弱性確認(必須)** | 新規にライブラリを追加する前に、**必ず最新のCVE情報・脆弱性情報を確認**し、既知の脆弱性がないことを確認してから導入する。確認方法の例:<br>- `pnpm audit` の実行<br>- [GitHub Advisory Database](https://github.com/advisories) での検索<br>- [npm 公式パッケージページ](https://www.npmjs.com/) の脆弱性表示確認<br>- [OSV.dev](https://osv.dev/) でのパッケージ名検索 |
| **既存依存の定期監査** | 定期的に `pnpm audit` を実行し、既存ライブラリに新規発見された脆弱性がないか確認する |
| **メンテナンス状況の確認** | 最終更新日が極端に古い、メンテナが実質不在、ダウンロード数が極端に少ない等のライブラリは、機能が同等でも採用を避ける |
| **lockfile の管理** | `pnpm-lock.yaml` を必ずリポジトリにコミットし、依存バージョンを固定する |

**運用フロー(ライブラリ追加時):**

1. 本当にライブラリが必要か再検討する(自前実装で十分な範囲か確認)
2. 候補ライブラリのCVE・脆弱性情報を確認する(上記の確認方法を使用)
3. 問題がなければ `pnpm add <package>` で追加する
4. 追加後、`pnpm audit` を実行し、警告が出ていないことを確認する
5. `pnpm-lock.yaml` の変更をコミットする


## 10. 制約条件

- 個人開発のため、開発・保守リソースは限定的
- 機微情報を扱うため、セキュリティ設計を最優先とする
- 既存パスワード管理ツール(1Password、Google パスワードマネージャー、Apple パスワード等)との役割分担を明確にする
  - パスワード自体の保管・自動入力: 各パスワードマネージャー側の役割
  - 「どこに何が保存されているか」「アカウント同士がどう紐づいているか」の可視化: 本アプリの役割

## 11. 今後の検討事項(オープンクエスチョン)

- 既存のパスワードマネージャーと連携するか、完全に独立したツールにするか
- モバイル対応の優先度、対応する場合のAPI認証方式(Cloudflare Access Service Tokens等)
- 紐づけ関係図のUI(ツリー型 / グラフ型 / マインドマップ型)の具体的な仕様
- 「保存先ツールを開く」ボタンから各パスワードマネージャー(アプリ/拡張機能)を直接起動できるようにするか(ディープリンク対応の要否)
- 保存先ツールの選択肢は固定リストにするか、ユーザーが自由に追加できるようにするか
- 独自ドメインを新規取得するか、既存の保有ドメインのサブドメインを利用するか
